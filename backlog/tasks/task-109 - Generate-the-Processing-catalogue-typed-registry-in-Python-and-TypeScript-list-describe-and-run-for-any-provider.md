## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
decision-64. Today ctx.algorithms.execute() accepts two hand-written requests (BufferRequest, CentroidRequest). This task makes every algorithm the host's QgsApplication.processingRegistry() holds reachable through one typed surface - native, qgis, gdal, 3d, pdal and any third-party provider the user installed (SAGA, GRASS, OTB) - with the typing generated from the registry itself rather than written by hand. Three parts: (1) a generic runtime surface list/describe/run on ctx.algorithms whose run allocates the destination parameters the caller leaves out under the run directory and returns owned layers, FileRefs or scalars (decision-19 kept: a failed run leaves no output); (2) a generator, qgis-sdk processing generate, that runs the registry reader inside the project's QGIS install and emits per provider a Python module (a TypedDict and a request class per algorithm, validated before any data is read, plus REGISTRY) and a TypeScript module (per-algorithm params/result types and an AlgorithmRegistry map) with --check for drift, following bridge generate; (3) a snapshot of the core providers (native, qgis, gdal, 3d, pdal) shipped in the runtime as qgis_sdk.processing.<provider>, regenerated by script from the pinned QGIS 4 and drift-checked in CI, so authors have typing without running the generator and the fake can answer list/describe. The bridge gets algorithms.list/describe/run as grantable host operations and a runAlgorithm(qgis, id, params) typed by the generated registry. Pulled forward from TASK-94, which keeps model files and batch runs.
