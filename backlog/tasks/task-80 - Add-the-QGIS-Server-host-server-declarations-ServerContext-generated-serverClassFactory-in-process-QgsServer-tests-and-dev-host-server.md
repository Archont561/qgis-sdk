## Description

decision-52 points 1, 2, 4. [tool.qgis-sdk] hosts; @server.filter(priority=), @server.service(name=, version=), @server.access_control on plain functions with an injected ServerContext (curated services over the request project, request and response as plain models; never QgsServerInterface); build generates serverClassFactory and server=True in metadata.txt; check HOST001/HOST002; qgis_sdk.testing fakes for request/response and a QgsServer in-process runner for test --target server; dev --host server with a local QgsServer loop and reload; scaffold --host server; reference example server variant; jobs request-scoped unless plugin-owned; agent endpoint developer-mode only on this host.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Ordering and request models (decision-69 point 1). Filters and services run by priority ascending, then the plugin class's own declaration order, then the declaration order of each included plugin, fixed when the runtime starts; a hook never depends on dict iteration or sort stability. ServerRequest.param(name, default=None) matches QgsServer's case-insensitive OGC lookup, params is a read-only case-insensitive view and headers is case-insensitive; ServerResponse carries status, headers and body plus text/json/xml/stream and set_header. Every @server.* decorator works bare and called. A request-scoped job is abandoned when its response is sent; plugin-owned work continues.

Server bindings availability, checked 2026-10-30 - this is why the native claim is now #2 and not part of #1. qgis.server exists only in a QGIS built with WITH_SERVER=ON plus WITH_BINDINGS: QGIS 4.2 CMakeLists defaults WITH_SERVER to FALSE and makes WITH_SERVER_PLUGINS follow WITH_BINDINGS. conda-forge turns it off deliberately (recipe/build.sh and bld.bat both pass -D WITH_SERVER=FALSE), so the pixi environment this workspace uses has no libqgis_server, no qgis/server, no _server.so and no qgis_mapserv.fcgi, and 'from qgis.server import QgsServer' is ModuleNotFoundError there. Routes that do provide it: apt qgis-server plus python3-qgis from the qgis.org or Debian repositories, the official qgis.org Windows/macOS installers (probe with python -c 'from qgis.server import QgsServer'), a source build with -DWITH_SERVER=ON -DWITH_BINDINGS=ON, and the qgis/qgis-server Docker images. Consequences: the scripted fake QgsServerInterface is what makes #1 and #3-#5 provable in this workspace, and it is what test --target server needs anyway; #2 sits behind a skip so a build with server bindings lights it up for free, and it has to be proved by the CI row rather than locally; the gate at TASK-83 records the row as run or blocked with this evidence.
Step 1 landed (2026-10-30, first slice): `[tool.qgis-sdk] hosts` is read and validated by the tools (default `["desktop"]`, an unknown name is CONFIG001), `qgis_sdk.core.Host` (`desktop`/`server`/`app`, a StrEnum with `gui`) is what the host that builds a context states, and `ctx.host` reports it on `PluginContext` and `UiContext` - a view inherits the host of the plugin context that opened it. `check` gained HOST001 (a Desktop-only declaration - `@toolbar`/`@menu`/`@shortcut`, a `Dialog`/`Dock` surface, a `[tool.qgis-sdk.web]` page - in a project whose hosts exclude `desktop`) and HOST003 (the `server` host declared while the visible QGIS has no `qgis.server`; a warning, because the environment is what is missing, and silent when no QGIS is visible at all). HOST002 waits for the server declarations themselves, since there is nothing to recognise by name until `@server.*` exists.
Step 2a landed (2026-10-30): the QGIS-free half of the server host. `qgis_sdk.server` carries `ServerRequest` (case-insensitive OGC parameters and headers, immutable, `with_params` to rewrite), `ServerResponse` (status, case-insensitive headers, `write_text`/`write_json`/`write_xml`, `text`/`xml`/`json`/`denied` constructors), `ServerContext` (host fixed to `Host.SERVER`, `request`/`response`/`scope` required, `project`/`layers`/`log` as capabilities refused by name, no `workers`/`ui`/`desktop`), the three decorators `filter(priority=)`, `service(name=, version=)` and `access_control(priority=)` - bare and called - and `ServerHooks`, which validates the signature each kind takes ((ctx, request, response), (ctx, request), (ctx, request, layer)), refuses an `async def`, an unannotated context, a non-int priority and two services claiming one name, and fixes the order once. `ServerHost` registers through a `ServerInterface` protocol (`register_filter`/`register_service`/`register_access_control`) and serves linearly: filters by priority, then declaration order, then included plugins; a filter returns None to pass, a `ServerRequest` to rewrite what the hooks after it see, or a `ServerResponse` to answer and stop; the access hooks rule on every requested layer before any service renders it; a service nobody serves is a 400 naming the SERVICE. `qgis_sdk.testing.FakeServerInterface` is the scripted interface, so 38 pure tests prove the three claims of #1 (a filter rewriting a WMS GetCapabilities request, a service answering its own request, an access hook refusing one layer) without QGIS. The refusal contract, decided here because #1 needed it: a hook says no by returning `ServerResponse.denied(reason, status=403)`, an access hook says no by returning `False` and the host builds that 403 naming the layer, and a hook that wants a different refusal writes it to `ctx.response` first. Still to do for #1: the adapter that turns these hooks into `QgsServerFilter`/`QgsService`/`QgsAccessControlFilter` over a real `QgsServerInterface`, and the codegen that emits `serverClassFactory`.

The AC's "4.2 channel" clause is read through decision-70: qgis.org's apt repository ships the 3.44 LTS, so the row proves the claims on the build a Linux user can install, and the 4.x server stays out of scope until 4.x reaches apt.

The row found three defects in the adapter rather than in the tests, and each is now a rule: `QgsAccessControl::fillCacheKey` treats a non-empty `cacheKey()` as "do not reuse a capabilities document", so an adapter whose layer decision varies per request and answers `""` hands one caller's document to another - it now answers with a key and pays one render per request; `QgsServer` holds one static server interface per process, so a filter registered by one test rewrote the next test's request, and every hook in the module now recognises its own request by a marker or a layer name; and `QgsRequestHandler` exposes the URL, the headers and the merged parameters but not the HTTP verb, so a filter hook sees `request.method == ""` rather than a plausible `GET`. The wiring itself is proven on every run by `tests/qgis_server_support.py` + `tests/test_server_wire.py` + `tests/test_server_adapter.py` (27 pure tests), and `tests/test_server_adapter_native.py` proves that a QGIS without `qgis.server` imports the adapter and refuses a host by name.
HOST002 landed (2026-10-30), the half of AC 3 that needed the declarations first: `check` now reports a `@server.filter`/`@server.service`/`@server.access_control` in a plugin whose `[tool.qgis-sdk] hosts` does not declare `server`, at the decorator's line, naming the hook and the declared set, with the same remediation shape as HOST001. It reads only `qgis_sdk.server` - the SDK does not re-export the three names at the top level, because `filter` and `service` are ordinary words and a plugin should say which host it is writing for - so a decorator of the same name from anywhere else is not a finding. The two rules are now independent passes over one parse: a project declaring neither host answers for both kinds. Still open in AC 3: a request-scoped job abandoned when its response is sent (the server host needs a job service and a scope it can quiesce with a zero deadline, per the decision-52 note), and the Desktop-bindings half is asserted by `ServerContext`'s capability set rather than by a two-host plugin test.
Request-scoped jobs landed (2026-10-30), the last mechanical half of AC 3. `ServerContext` gained a `jobs` capability - a `Jobs` facade over the *request* scope - and the server host is what derives it: `ServerHost(hooks, interface, jobs=service)` builds `Jobs(service.request_scoped(scope))` in `context()`, so `ctx.jobs.<name>` is this request's work while `ctx.jobs.plugin.<name>` keeps the plugin's lifetime. `JobService.request_scoped` is the sibling of `scoped` with the other disposal rule: its service registers `on_close` on the request scope, so the response's scope close *is* the abandonment. Abandoning there (`_Attempt.cancelled_by_request`) sets the handle's `status` to `JobStatus.CANCELLED` immediately - the answer is the host's word, not a worker report no pump would ever deliver - asks a running worker to stop, closes the attempt's scope, and drops the job out of the scheduler through a new `StepScheduler.abandon(job)` (the same rule `dispose` applies to a whole scope, with a later worker report counted as dropped rather than delivered). No callback runs. The plugin-unload path is deliberately unchanged: there the scheduler's own verdict - `QgisSdkScopeClosedError` for a job that never started, `cancelled` for one that did - is more informative, so the request rule is a second policy rather than an edit to the first. The request is the clock, per decision-52's note: `ServerHost.tick()` runs at request start, and `QgsServerHost` calls it from `serve_filter` and `serve_service`, which is also where the per-request scope is closed. Eight pure tests in `tests/test_server_jobs.py` pin it: the request owns what a hook submits, the response reports `cancelled` with `owner_closed`, `QgisSdkJobCancelledError` from `get()`/`result` and no callbacks, the plugin's scheduler keeps nothing, a plugin-owned job survives the response and still delivers, the request ticks a job one step at a time, a spent request scope refuses new work, a host with no job service refuses `jobs` by name, and `FakeServerInterface.serve(..., jobs=...)` derives the same scope. Still open in AC 3: the two-host claim as one test - the Desktop half is asserted today by `ServerContext`'s capability set (no `ui`/`desktop`/`views`/`workers`), not by running one plugin class on both hosts, and that single-plugin-class test belongs with the generated `serverClassFactory` in AC 4.
AC 4 started (2026-10-30) with the scaffold and `build`, both QGIS-free and both provable here. `qgis-sdk new --host server` writes the same six files as a Desktop project and differs in two: `[tool.qgis-sdk] hosts = ["server"]`, and `<plugin>/__init__.py` holds `HOOKS = ServerHooks((default_version, answer, everything_public))` plus `serverClassFactory(serverIface)` - QGIS Server imports the package and calls that name, so unlike `classFactory` (appended by `build`/`dev`, decision-43) it has to exist in the source tree. `<plugin>/plugin.py` declares one of each hook, and `tests/test_plugin.py` drives them through `FakeServerInterface`, so the starter tests still need no QGIS. The flags only one host can honour are refused instead of silently dropped: `--web`, `--ui` and `--algorithm` need `iface` or a Processing registry and a `ServerContext` has neither. On the build side, `render_metadata` writes `server=True` when `hosts` declares the server (Desktop ignores the key, so one ZIP serves both hosts) and `_entry_points` appends `classFactory` only to a project that declares `desktop`, leaving a server-only package's own entry alone. Thirteen pure tests in `tests/test_scaffold_server.py` pin the plan, the refusal messages, the generated package importing without QGIS, its own starter tests passing in a bare interpreter, `check` accepting it (no HOST001/HOST002) and the metadata derivation; two more in `test_scaffold_cli.py` pin the flag and the refusal. Still open in AC 4: `test --target server` (the `server` marker exists in the test layers, but `TARGETS` in `qgis_sdk_tools.devtools.testrun` has no such target yet) and `dev --host server` (a local `QgsServer` loop with reload).

AC 3 closed (2026-10-30): the same plugin class, unchanged, runs on both hosts. `tests/test_two_host_plugin.py` declares one module - `app` with a `@toolbar` action, plus a `@filter`, a `@service` and an `@access_control` hook, and the `HOOKS` a generated entry exports - writes it as a project whose `hosts = ["desktop", "server"]`, and runs it both ways without QGIS: `qgis_sdk.adapters.desktop.host(...)(None)` starts the real Desktop lifecycle and the action reads `ctx.host.value == "desktop"`, while `ServerHost`/`FakeServerInterface` serves the same object's hooks and the service reads `"server"`. The two declaration surfaces stay separate - `describe(app).actions` is `["ping"]` and the hook set is the other three names - and each host sees only its own: the server registers one chain filter, one service and one access-control object, and the Desktop action appears nowhere in that. The server context has no `desktop` and no `ui` attribute at all and refuses `jobs`/`project` by name, so "refuses by name on the server" is the capability contract, not a special case. The project checks clean (no HOST001/HOST002), and the same module declaring one host at a time fires HOST002 (desktop only) and HOST001 (server only), which is what makes the clean run mean something.

AC 4 closed (2026-10-30), both halves. `qgis-sdk test --target server` is a native target like `qgis` and `desktop`: the `server` marker, `-m server` selection, the install's interpreter, `QT_QPA_PLATFORM=offscreen` and `QGIS_SDK_TEST_TARGET=server`, the skip gate (every test skipped fails the run) and a bindings gate of its own - `configured_bindings_error` refuses the session with the build that has `qgis.server`, because a conda-forge QGIS imports `qgis.core` happily and would otherwise skip its way to a green run. `qgis-sdk dev --host server` (`--host` is the same flag as `--mode`, since `new --host server` and `test --target server` name the same axis) is the local loop: `plan_dev(mode="server", port=...)` writes `dev-server.py`, which starts a headless `QgsApplication` and one `QgsServer` in the process and answers HTTP on loopback through `QgsServer.handleRequest` with a buffered request and response - no FCGI, no Desktop, no profile, no Vite (a server-only project cannot declare a page). The plugin loads through the generated host package's `serverClassFactory`; a saved change re-imports the sources and hands QGIS's registration the new hook set, because the server interface cannot withdraw a filter, a service or an access-control object. Two limits are stated instead of discovered: the entry module must export `HOOKS = ServerHooks((...))` (the scaffold's name) for a reload to find the new hooks, and a changed priority or service identity is refused by name because the registration froze both - it needs a new `qgis-sdk dev`. A reload that fails leaves the endpoint answering 503 with the reason in the body and on the terminal, never a half-loaded plugin, because the loop is single-threaded and reloads between requests. Evidence: `tests/test_server_devtools.py` (17 pure tests - first load through the factory, rebind through the held objects, a changed service identity disabled with the reason, an import that raises, `forget`, the empty quiesce, request translation, the 503 body, the tick, a real socket round trip), `TestServerPlan` in `test_devtools_dev.py`, `test_host_server_runs_the_interpreter_with_a_server_loop` in `test_devtools_dev_cli.py`, and `tests/test_server_devtools_native.py` on the `QGIS 3.44 LTS` row (opted in with `QGIS_SDK_SERVER_DEV=1`), which spawns the CLI, waits for the port, asserts the service answers, edits the filter and asserts the *next* body is the edited one - a reload, not a restart. Doc-12 documents the target and the mode, including what a reload cannot change; doc-14 lists the third module on the row.

The native proof ran (2026-10-30) and found two things the pure tests could not. The `QGIS 3.44 LTS` row exports `QGIS_PREFIX_PATH=/usr`, and `find_qgis_install` refused it: `python3-qgis` keeps its bindings in `lib/python3/dist-packages`, a layout `BINDINGS_LAYOUTS` did not know, so the only QGIS on the machine looked like no QGIS at all - the layout is now discovered, and `_resolve` takes the first layout that actually carries the `qgis` package rather than the first that exists, because a Debian prefix has a `share/qgis` resource tree beside the bindings. The second was a wrong claim in the documentation and in the loop's own advice: `QgsServer::handleRequest` dispatches a `SERVICE` only when it has a project (`qgsserver.cpp`, "Project file error. For OWS services..."), a plugin answering its own service included, so a MAP-less request answered `500` on every attempt. The loop now passes `handleRequest` an empty `QgsProject` - built once, because every request installs it as the current project - and passes `None` when the request names `MAP`, leaving that file to QGIS's own loading; `query_server` takes the project as a parameter so the pure tests pin both halves. Two smaller things came out of the same run: `ServerLoop.respond` answers a raised exception with `500` and the traceback in the body (a bare `500` with the reason only in a log the terminal never showed is what cost the first two runs), and `bind()` reports the port the socket got, so port `0` is usable. Evidence (run 41142490003, job 124359830276): `LTS host: qgis 3.44.7-Solothurn | qgisserver QgsServer | qt 5.15.13 | binding PyQt5`, `test_server_devtools_native.py` 2 passed, `test_server_native.py` 7 passed, `test_lts_native.py` 7 passed - the second dev-loop test being the AC's claim, a saved filter edit answering the next request without a restart.

AC 1 and AC 5 closed by evidence (2026-10-30). #5 was already satisfied where it says it would be: `test_filters_run_by_priority_then_declaration_order` and `test_included_hooks_run_after_the_plugins_own` pin the order decision-69 point 1 fixes, doc-12 states it in the same words ("priority ascending, then the plugin class's declaration order, then include order"), and the case-insensitive `ServerRequest` helpers plus the `text`/`xml`/`json`/`denied` constructors have their own tests in `test_server_host.py`. #1 was not: the three claims were proven through `ServerHost`/`FakeServerInterface`, never through the `serverClassFactory` the scaffold writes, and that factory could not run purely because `qgis_sdk.adapters.qgis` imported every adapter - `.algorithms` first - the moment any name was asked for. The package now resolves a name on first access, which is what the server adapter's own docstring always claimed for it: `tests/test_server_factory.py` writes a `--host server` project, installs the `qgis.server` stand-ins, imports the generated package, calls its `serverClassFactory` and drives what it registered - one chain filter at the default priority 30, one `QgsService` named `DEMOSERVER` at `1.0.0`, one access-control object. The filter rewrites the request QGIS will serve (`VERSION=1.3.0` reaches the request handler), the service answers through the response QGIS handed it, an edited access hook refuses a layer by clearing all four `LayerPermissions`, and `cacheKey()` stays non-empty so a capabilities document is never reused across requests. `tests/test_pure_imports.py` adds the companion rule in a subprocess with `qgis`/`PyQt5`/`PyQt6` forbidden: `qgis_sdk.adapters.qgis.server` and the package import without any native module, and `.algorithms` is not imported on the way.
