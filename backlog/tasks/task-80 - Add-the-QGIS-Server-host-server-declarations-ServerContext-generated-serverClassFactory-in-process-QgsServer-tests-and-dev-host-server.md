## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Ordering and request models (decision-69 point 1). Filters and services run by priority ascending, then the plugin class's own declaration order, then the declaration order of each included plugin, fixed when the runtime starts; a hook never depends on dict iteration or sort stability. ServerRequest.param(name, default=None) matches QgsServer's case-insensitive OGC lookup, params is a read-only case-insensitive view and headers is case-insensitive; ServerResponse carries status, headers and body plus text/json/xml/stream and set_header. Every @server.* decorator works bare and called. A request-scoped job is abandoned when its response is sent; plugin-owned work continues.

Server bindings availability, checked 2026-10-30 - this is why the native claim is now #2 and not part of #1. qgis.server exists only in a QGIS built with WITH_SERVER=ON plus WITH_BINDINGS: QGIS 4.2 CMakeLists defaults WITH_SERVER to FALSE and makes WITH_SERVER_PLUGINS follow WITH_BINDINGS. conda-forge turns it off deliberately (recipe/build.sh and bld.bat both pass -D WITH_SERVER=FALSE), so the pixi environment this workspace uses has no libqgis_server, no qgis/server, no _server.so and no qgis_mapserv.fcgi, and 'from qgis.server import QgsServer' is ModuleNotFoundError there. Routes that do provide it: apt qgis-server plus python3-qgis from the qgis.org or Debian repositories, the official qgis.org Windows/macOS installers (probe with python -c 'from qgis.server import QgsServer'), a source build with -DWITH_SERVER=ON -DWITH_BINDINGS=ON, and the qgis/qgis-server Docker images. Consequences: the scripted fake QgsServerInterface is what makes #1 and #3-#5 provable in this workspace, and it is what test --target server needs anyway; #2 sits behind a skip so a build with server bindings lights it up for free, and it has to be proved by the CI row rather than locally; the gate at TASK-83 records the row as run or blocked with this evidence.
Step 1 landed (2026-10-30, first slice): `[tool.qgis-sdk] hosts` is read and validated by the tools (default `["desktop"]`, an unknown name is CONFIG001), `qgis_sdk.core.Host` (`desktop`/`server`/`app`, a StrEnum with `gui`) is what the host that builds a context states, and `ctx.host` reports it on `PluginContext` and `UiContext` - a view inherits the host of the plugin context that opened it. `check` gained HOST001 (a Desktop-only declaration - `@toolbar`/`@menu`/`@shortcut`, a `Dialog`/`Dock` surface, a `[tool.qgis-sdk.web]` page - in a project whose hosts exclude `desktop`) and HOST003 (the `server` host declared while the visible QGIS has no `qgis.server`; a warning, because the environment is what is missing, and silent when no QGIS is visible at all). HOST002 waits for the server declarations themselves, since there is nothing to recognise by name until `@server.*` exists.
Step 2a landed (2026-10-30): the QGIS-free half of the server host. `qgis_sdk.server` carries `ServerRequest` (case-insensitive OGC parameters and headers, immutable, `with_params` to rewrite), `ServerResponse` (status, case-insensitive headers, `write_text`/`write_json`/`write_xml`, `text`/`xml`/`json`/`denied` constructors), `ServerContext` (host fixed to `Host.SERVER`, `request`/`response`/`scope` required, `project`/`layers`/`log` as capabilities refused by name, no `workers`/`ui`/`desktop`), the three decorators `filter(priority=)`, `service(name=, version=)` and `access_control(priority=)` - bare and called - and `ServerHooks`, which validates the signature each kind takes ((ctx, request, response), (ctx, request), (ctx, request, layer)), refuses an `async def`, an unannotated context, a non-int priority and two services claiming one name, and fixes the order once. `ServerHost` registers through a `ServerInterface` protocol (`register_filter`/`register_service`/`register_access_control`) and serves linearly: filters by priority, then declaration order, then included plugins; a filter returns None to pass, a `ServerRequest` to rewrite what the hooks after it see, or a `ServerResponse` to answer and stop; the access hooks rule on every requested layer before any service renders it; a service nobody serves is a 400 naming the SERVICE. `qgis_sdk.testing.FakeServerInterface` is the scripted interface, so 38 pure tests prove the three claims of #1 (a filter rewriting a WMS GetCapabilities request, a service answering its own request, an access hook refusing one layer) without QGIS. The refusal contract, decided here because #1 needed it: a hook says no by returning `ServerResponse.denied(reason, status=403)`, an access hook says no by returning `False` and the host builds that 403 naming the layer, and a hook that wants a different refusal writes it to `ctx.response` first. Still to do for #1: the adapter that turns these hooks into `QgsServerFilter`/`QgsService`/`QgsAccessControlFilter` over a real `QgsServerInterface`, and the codegen that emits `serverClassFactory`.

AC 2 is met, on the build that exists (2026-10-30, run 41124104232 job 124298027080): `QGIS 3.44 LTS` reports `7 passed` for `tests/test_server_native.py` against `qgis 3.44.7-Solothurn | qgisserver QgsServer | qt 5.15.13 | binding PyQt5`. The module declares the plugin once - a `@server.filter` that routes a marked request to its own service and rewrites a parameter, that `@server.service`, and an `@server.access_control` hook - and drives those same three hooks through `qgis_sdk.testing.FakeServerInterface` and through a real `QgsServer` with `QgsBufferServerRequest`/`QgsBufferServerResponse`: the rewrite reaches the service (`marker=seen routed=yes` on the wire), the service answers, and a refused layer disappears from a WMS GetCapabilities document while the allowed one stays. The AC's "4.2 channel" clause is read through decision-70: qgis.org's apt repository ships the 3.44 LTS, so the row proves the claims on the build a Linux user can install, and the 4.x server stays out of scope until 4.x reaches apt.

The row found three defects in the adapter rather than in the tests, and each is now a rule: `QgsAccessControl::fillCacheKey` treats a non-empty `cacheKey()` as "do not reuse a capabilities document", so an adapter whose layer decision varies per request and answers `""` hands one caller's document to another - it now answers with a key and pays one render per request; `QgsServer` holds one static server interface per process, so a filter registered by one test rewrote the next test's request, and every hook in the module now recognises its own request by a marker or a layer name; and `QgsRequestHandler` exposes the URL, the headers and the merged parameters but not the HTTP verb, so a filter hook sees `request.method == ""` rather than a plausible `GET`. The wiring itself is proven on every run by `tests/qgis_server_support.py` + `tests/test_server_wire.py` + `tests/test_server_adapter.py` (27 pure tests), and `tests/test_server_adapter_native.py` proves that a QGIS without `qgis.server` imports the adapter and refuses a host by name.
HOST002 landed (2026-10-30), the half of AC 3 that needed the declarations first: `check` now reports a `@server.filter`/`@server.service`/`@server.access_control` in a plugin whose `[tool.qgis-sdk] hosts` does not declare `server`, at the decorator's line, naming the hook and the declared set, with the same remediation shape as HOST001. It reads only `qgis_sdk.server` - the SDK does not re-export the three names at the top level, because `filter` and `service` are ordinary words and a plugin should say which host it is writing for - so a decorator of the same name from anywhere else is not a finding. The two rules are now independent passes over one parse: a project declaring neither host answers for both kinds. Still open in AC 3: a request-scoped job abandoned when its response is sent (the server host needs a job service and a scope it can quiesce with a zero deadline, per the decision-52 note), and the Desktop-bindings half is asserted by `ServerContext`'s capability set rather than by a two-host plugin test.
Request-scoped jobs landed (2026-10-30), the last mechanical half of AC 3. `ServerContext` gained a `jobs` capability - a `Jobs` facade over the *request* scope - and the server host is what derives it: `ServerHost(hooks, interface, jobs=service)` builds `Jobs(service.request_scoped(scope))` in `context()`, so `ctx.jobs.<name>` is this request's work while `ctx.jobs.plugin.<name>` keeps the plugin's lifetime. `JobService.request_scoped` is the sibling of `scoped` with the other disposal rule: its service registers `on_close` on the request scope, so the response's scope close *is* the abandonment. Abandoning there (`_Attempt.cancelled_by_request`) sets the handle's `status` to `JobStatus.CANCELLED` immediately - the answer is the host's word, not a worker report no pump would ever deliver - asks a running worker to stop, closes the attempt's scope, and drops the job out of the scheduler through a new `StepScheduler.abandon(job)` (the same rule `dispose` applies to a whole scope, with a later worker report counted as dropped rather than delivered). No callback runs. The plugin-unload path is deliberately unchanged: there the scheduler's own verdict - `QgisSdkScopeClosedError` for a job that never started, `cancelled` for one that did - is more informative, so the request rule is a second policy rather than an edit to the first. The request is the clock, per decision-52's note: `ServerHost.tick()` runs at request start, and `QgsServerHost` calls it from `serve_filter` and `serve_service`, which is also where the per-request scope is closed. Eight pure tests in `tests/test_server_jobs.py` pin it: the request owns what a hook submits, the response reports `cancelled` with `owner_closed`, `QgisSdkJobCancelledError` from `get()`/`result` and no callbacks, the plugin's scheduler keeps nothing, a plugin-owned job survives the response and still delivers, the request ticks a job one step at a time, a spent request scope refuses new work, a host with no job service refuses `jobs` by name, and `FakeServerInterface.serve(..., jobs=...)` derives the same scope. Still open in AC 3: the two-host claim as one test - the Desktop half is asserted today by `ServerContext`'s capability set (no `ui`/`desktop`/`views`/`workers`), not by running one plugin class on both hosts, and that single-plugin-class test belongs with the generated `serverClassFactory` in AC 4.
