## Description and exit criteria

Questionnaires and non-interactive templates, check/test/dev/build, controlled
refresh and private pure-Python-first runtime packaging. On the TypeScript side
this is the milestone where the bridge stops being an SDK-internal artifact and
becomes a **consumed dependency**: generated vanilla and React projects pin it,
the development loop reconnects through the connection lifecycle it defines, and
the plugin ZIP ships its built bundle.

Exit criteria, both required:

- **`qgis-sdk`** — scaffolds, check/test/dev/build, refresh/reconnection,
  diagnostics and ZIP packaging pass their own criteria with recorded evidence.
- **`@archont561/qgis-sdk-bridge`** — the generated scaffolds that ship a
  `QWebEngineView` (vanilla and React) install the bridge at the milestone
  version, typecheck, build and pass their isolated harnesses offline; the
  packaged ZIP carries production frontend assets, excludes dev-server assets
  (TASK-8 AC #2) and imports nothing workspace-only.

| Artifact | Registry | Planned delta since 0.3.0 |

## Bridge changes in this milestone

| Change to `packages/qgis-sdk-bridge` | Task | Resulting bridge version |
| --- | --- | --- |
| None planned. The generated projects and the packaged ZIP consume 0.2.x; consuming a surface is not changing it. | TASK-19, TASK-8 | unchanged |
| Only if a consumer proves the published surface insufficient, the fix lands as a source change recorded here. | TASK-21 or TASK-8 | 0.2.x patch |

No bridge source change is planned in this milestone, and that is a claim the
release gate has to test rather than assume:

- **[TASK-19](../tasks/task-19%20-%20Scaffold-vanilla-and-React-web-projects-through-validated-questionnaires.md)**
  generates projects that depend on `@archont561/qgis-sdk-bridge` at the
  matching version. The scaffold must pin the pair, not a floating range, so a
  generated project can never be built against a bridge the Python SDK it ships
  with was not tested against.
- **[TASK-21](../tasks/task-21%20-%20Implement-generation-safe-development-refresh-and-reconnection.md)**
  consumes the connection lifecycle and reconnect semantics defined in m-2. If
  it turns out the published lifecycle cannot express generation-safe refresh,
  the correction lands in the bridge and is recorded here as a source change —
  do not paper over it in the scaffold.
- **[TASK-8](../tasks/task-8%20-%20Build-a-validated-QGIS-installable-plugin-ZIP.md)**
  packages production frontend assets, so the bridge's published `files` list
  and export map are exercised by something other than its own tests for the
  first time: a build that only resolves inside the workspace fails here.

A milestone that needs no bridge change does not release it
([decision-25](../decisions/decision-25%20-%20Version-each-package-independently-behind-a-shared-contract-version.md)):
the bridge stays at 0.2.x, no npm version is consumed, and TASK-30 verifies the
Python manifests at 0.4.0 plus the contract version across both languages. If
TASK-19, TASK-21 or TASK-8 does force a change, it is a real `ts-v0.2.x` patch
release at the bridge's own version, recorded here as a surface change.

## Version policy

0.4.0 is a SemVer planning target, not a published version. Experimental 0.x
breaking changes require a documented minor release; patches are compatible
fixes. Prereleases may use 0.4.0-alpha.1 or 0.4.0-beta.1. Do not bump manifests
during planning. Feature and fix work inside the milestone bumps only the patch;
the minor advances at the milestone close by an explicit `--bump minor`.
`qgis-sdk` and `qgis-sdk-bridge` carry **independent** versions, each derived
from its own commits and stamped by its own release tag ([decision-25](../decisions/decision-25%20-%20Version-each-package-independently-behind-a-shared-contract-version.md));
0.4.0 releases Python only unless the bridge needs a fix. A shared
plugin-description contract version is what pairs them. Stable 1.0.0 requires a later
explicit API-stability decision.
