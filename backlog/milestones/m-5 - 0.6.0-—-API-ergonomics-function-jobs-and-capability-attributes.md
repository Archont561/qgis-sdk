## Description and exit criteria

The first minor after the qualified 0.5.0 reference release, cut because two
breaking changes to the author-facing runtime API landed on `main` right after
it and a breaking change in an experimental 0.x line is a documented minor,
not a patch: `@job` became a plain function with the `JobContext` injected
([decision-38](../decisions/decision-38%20-%20Declare-jobs-as-plain-functions-with-the-JobContext-injected.md),
PR #86) and the optional services on every context became capability
attributes that refuse by name, replacing `require_<name>()`
([decision-39](../decisions/decision-39%20-%20Expose-optional-services-as-capability-attributes-that-refuse-by-name.md),
PR #87). Both are already documented in doc-12's 0.6.0 migration notes. A
third change joined afterwards: the ergonomic refactor of the bridge package
([decision-40](../decisions/decision-40%20-%20Make-the-root-entry-the-page-import-and-keep-generated-plugin-clients-import-free.md), [TASK-61](../tasks/task-61%20-%20Make-the-bridge-root-entry-the-page-import-and-prefix-the-generated-contract-errors.md)) - the root entry re-exports the transport client, the
never-raised Python-error mirrors leave it, and the generated contract errors
carry the `QgisSdk` prefix and the wire code - which is a 0.x minor of
`@archont561/qgis-sdk` and a generator change in `qgis-sdk-tools`. A fourth,
tooling-side: the scaffolded page's bridge dependency is now owned by the
release pipeline - an exact pin that `release.py stamp --scope typescript`
moves and `verify-versions` checks - and switched to the workspace bridge
inside this repository only through the explicit `--sdk-dependency` flag
([decision-41](../decisions/decision-41%20-%20Pin-the-scaffolded-page-to-the-released-bridge-and-switch-it-to-the-workspace-bridge-only-by-explicit-flag.md), [TASK-62](../tasks/task-62%20-%20Scaffold-the-page-on-the-pinned-bridge-release-for-users-and-on-the-workspace-bridge-inside-the-repository.md)). Re-scoped on 2026-10-26 to
take two more authoring changes of the same kind rather than release around
them: algorithms become plain functions on providers the plugin lists
(`providers = [...]`, [decision-42](../decisions/decision-42%20-%20Declare-algorithms-as-plain-functions-on-providers-the-plugin-owns.md), [TASK-63](../tasks/task-63%20-%20Declare-algorithms-as-plain-functions-on-providers-the-plugin-owns.md)), and the QGIS
host artifacts - `metadata.txt`, `classFactory`, the page view - become
outputs of `build` and `dev` instead of scaffolded files ([decision-43](../decisions/decision-43%20-%20Generate-the-QGIS-host-artifacts-in-build-and-dev-instead-of-scaffolding-them.md),
[TASK-64](../tasks/task-64%20-%20Generate-metadata.txt-classFactory-and-the-page-view-in-build-and-dev.md), [TASK-65](../tasks/task-65%20-%20Scaffold-the-clean-project-and-migrate-the-reference-plugin.md)). Neither touches the wire. Two more
followed the same day: the page builds its typed client from a generated
schema module, `QgisSdk.fromBridgeSchema(schema)` ([decision-44](../decisions/decision-44%20-%20Generate-a-typed-bridge-schema-module-and-build-the-client-from-it-at-runtime.md),
[TASK-66](../tasks/task-66%20-%20Generate-the-typed-bridge-schema-module-and-add-QgisSdk.fromBridgeSchema.md)), and a native plugin binds actions to the Desktop with
stackable `@toolbar`/`@menu`/`@shortcut` decorators on actions and on
`Dialog`/`Dock` surface classes, `ctx.ui.open` and `UiContext.actions` ([decision-45](../decisions/decision-45%20-%20Bind-actions-to-the-Desktop-with-stackable-toolbar-and-menu-decorators-and-plain-surface-classes.md), [TASK-67](../tasks/task-67%20-%20Bind-actions-and-Dialog-Dock-surfaces-to-the-Desktop-with-toolbar-menu-shortcut-ctx.ui.open-and-UiContext.actions.md)). The
milestone is the release of what has landed; anything that joins it must keep
both migration notes honest.

Exit criteria, both required:

- **`qgis-sdk`** — `qgis-sdk-runtime`, `qgis-sdk-tools` and the `qgis-sdk`
  kit are released at 0.6.0 from one green gate (the 0.5.0 gate re-run over
  the new API: Python suite, `tests/scripts`, the example project, the opt-in
  harnesses the changes touched), with the migration note covering every
  removed or renamed name and `qgis-sdk check` still telling a 0.5 project
  what to change.
- **`@archont561/qgis-sdk`** — released at 0.4.0 from the same gate as the
  Python packages: `QgisSdk.fromBridgeSchema` over the generated schema module
  ([TASK-66](../tasks/task-66%20-%20Generate-the-typed-bridge-schema-module-and-add-QgisSdk.fromBridgeSchema.md)), the root-entry barrel and the renamed generated errors of
  [TASK-61](../tasks/task-61%20-%20Make-the-bridge-root-entry-the-page-import-and-prefix-the-generated-contract-errors.md), with doc-13's 0.4.0 migration notes covering every removed or
  renamed name. What crosses `QWebChannel` is unchanged - transport protocol
  `1`, plugin-description contract `1`, `HOST_SCHEMA_VERSION` `1` and the
  same `HOST_FINGERPRINT` as `ts-v0.3.0` - and `release.py verify-versions`
  shows the contract version agreeing across both languages.

## Version policy

0.6.0 is the next Python minor and 0.4.0 the next bridge minor; neither is
a published version until
[TASK-60](../tasks/task-60%20-%20Prepare-and-qualify-0.6.0-release.md) is
authorised. Experimental 0.x breaking changes require a documented minor
release; patches are compatible fixes. Prereleases may use `0.6.0-rc.N` for a
pipeline rehearsal (dry run, no uploads). Do not bump manifests during
planning. `qgis-sdk` and `@archont561/qgis-sdk` carry **independent** versions,
each derived from its own commits and stamped by its own release tag
([decision-25](../decisions/decision-25%20-%20Version-each-package-independently-behind-a-shared-contract-version.md));
a shared plugin-description contract version is what pairs them. Stable 1.0.0
requires a later explicit API-stability decision.
