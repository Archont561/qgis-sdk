## Description and exit criteria

The first v2 increment: plain class contexts, lifecycle ownership, curated
native services, class-based Processing algorithms with their toolbox
registration, and schema-driven native UI with handler dispatch. It releases
`qgis-sdk` alone — the bridge is not published, because no task here changes it
(see "Bridge track").

Exit criteria, both required:

- **`qgis-sdk`** — every feature task in the milestone closes with its own
  recorded evidence, including a real QGIS 4.2.3 host test wherever native
  behaviour is claimed. After the 2026-10-24 re-scope the only open feature is
  TASK-3 (schema-driven native UI and handler dispatch).
- **`@archont561/qgis-sdk-bridge`** — no release: `package.json` keeps 0.1.1,
  the bridge still builds and its tests pass, and the plugin-description
  contract version agrees across both languages at the gate.

## Scope after the 2026-10-24 re-scope

0.2.0 was scoped to five feature tasks. Three landed — TASK-25 with its five
slices, TASK-14 and TASK-39 — and two did not: TASK-5 (QGIS-aware HTTP client)
and TASK-15 (scoped local jobs). Both moved to [m-2](m-2%20-%200.3.0-%E2%80%94-typed-bridge-runtime-web-ui-networking-and-local-jobs.md)
rather than holding the release:

- they depend on nothing else in m-1 and unblock nothing in it, so keeping them
  only lengthened the tail of the milestone;
- neither is part of the "native runtime and Processing" surface the milestone
  is named for;
- both were blocked on design that was still *proposed* when they were moved —
  [decision-4](../decisions/decision-4%20-%20QGIS-aware-networking-uses-an-async-first-transport.md)
  for the networking transport and
  [decision-13](../decisions/decision-13%20-%20Use-runtime-bound-Celery-inspired-local-jobs.md)
  for job transport — so they needed design time rather than a rushed slice. Both
  were accepted on 2026-10-24, which is what lets m-2 open with the API settled.

What remains is a milestone that can close as soon as TASK-3 lands: the runtime,
the native services, the Processing algorithms and their toolbox registration
are implemented and evidenced.

## Bridge track

| Change to `packages/qgis-sdk-bridge` | Task | Resulting bridge version |
| --- | --- | --- |
| None. No file under `packages/qgis-sdk-bridge` is touched, so nothing is published and no npm version is consumed. | — | stays 0.1.1 |

0.2.0 releases **only** the Python package. The bridge is not published: its
source is identical to 0.1.1, no task in m-1 touches it, and npm versions are
immutable, so an unchanged release would consume a version to say nothing
([decision-25](../decisions/decision-25%20-%20Version-each-package-independently-behind-a-shared-contract-version.md)).
`packages/qgis-sdk-bridge/package.json` keeps 0.1.1 through the release.

That is a decision, not an omission. The standing m-1 position is no handwritten
TypeScript surface, and
[decision-18](../decisions/decision-18%20-%20Ship-a-framework-neutral-bridge-and-explicit-web-scaffolding-choices.md)
requires the typed surface to be *generated* — which needs TASK-4's transport
contract in m-2 rather than being invented a release early. The m-1 features
(native services, Processing and its registration, native UI) are Python
capabilities behind QGIS native widgets; none of them exports an action a web
view could call yet, so the bridge has nothing to mirror.

What the release still has to prove about the pair:

- The only Python-side break that reaches a paired consumer is
  `AlgorithmContext.algorithms` becoming required. It is a Python API break with
  no wire or type change, because no algorithm is reachable as a bridge action;
  the migration note belongs to the Python changelog.
- TASK-28 runs `release.py verify-versions --scope python --version 0.2.0`:
  `pyproject.toml` and `recipe.yaml` must carry 0.2.0, `package.json` must still
  carry 0.1.1, and the plugin-description contract version must agree across
  both languages. The bridge is otherwise built and its tests run by CI as
  usual — no packaging or publish step is skipped for it, because none happens.
- A bridge consumer stays on 0.1.1 and keeps working: Python 0.2.0 still emits
  `schema_version: 1`, which is what the contract check exists to confirm.

If a bridge change does become necessary in m-1 (a new error code, a contract
version bump forced by a Python wire change), it belongs to this milestone, and
it becomes a real `ts-v*` release at the bridge's own version. Record it here
rather than letting an undiscussed bridge delta ride along with the Python one.

## Version policy

0.2.0 is a SemVer planning target, not a published version. Experimental 0.x
breaking changes require a documented minor release; patches are compatible
fixes. Prereleases may use 0.2.0-alpha.1 or 0.2.0-beta.1. Do not bump manifests
during planning. When the milestone closes, the minor is set **explicitly**
(`release.py plan --bump minor`); feature and fix work inside the milestone only
bumps the patch, so automatic derivation proposes the patch and the milestone
release is a deliberate act. When 0.2.0 closes, only the Python package is
released: the bridge stays at 0.1.1 because no m-1 task changes its source.
`qgis-sdk` and `qgis-sdk-bridge` carry **independent** versions, each derived
from its own commits and stamped by its own release tag
([decision-25](../decisions/decision-25%20-%20Version-each-package-independently-behind-a-shared-contract-version.md));
a shared plugin-description contract version is what pairs them. Stable 1.0.0
requires a later explicit API-stability decision.
