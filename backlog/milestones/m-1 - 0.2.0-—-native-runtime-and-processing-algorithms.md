## Description and exit criteria

The first v2 increment on the Python side: plain class contexts, lifecycle
ownership, native dialogs/docks, Processing output safety, provider
registration and local jobs. It ships as a matched **pair** at 0.2.0, but only
`qgis-sdk` changes — the bridge is a deliberate no-source-change release (see
"Bridge track").

Exit criteria, both required:

- **`qgis-sdk`** — the remaining feature tasks close with their own recorded
  evidence, including a real QGIS 4.2.3 host test wherever native behaviour is
  claimed (TASK-3, TASK-5, TASK-15 for the 0.2.0 surface).
- **`@archont561/qgis-sdk-bridge`** — built, typechecked, tested and stamped at
  0.2.0 with the same source as 0.1.1, or with any change it does contain
  declared in this file and in the changelog.

## Bridge track

0.2.0 publishes the bridge at 0.2.0 with **no source change**. That is
deliberate, not an omission: the standing m-1 position is no handwritten
TypeScript surface, and [decision-18](../decisions/decision-18%20-%20Ship-a-framework-neutral-bridge-and-explicit-web-scaffolding-choices.md)
requires the typed surface to be *generated* — which needs TASK-4's transport
contract in m-2 rather than being invented a release early. The five m-1
features (native services, Processing, native UI, HTTP, local jobs) are all
Python-side capabilities behind QGIS native widgets; none of them exports an
action a web view could call yet, so there is nothing in the bridge to change.

What a bridge consumer sees in 0.2.0:

- The only Python-side break that reaches a paired consumer is
  `AlgorithmContext.algorithms` becoming a required field. It is a Python API
  break with no wire or type change, because no algorithm is reachable as a
  bridge action; migration notes belong to the Python changelog.
- The npm release must say so plainly: "alignment release; bridge surface
  unchanged since 0.1.1" ([decision-24](../decisions/decision-24%20-%20Release-the-Python-SDK-and-TypeScript-bridge-at-one-shared-version.md)).
- TASK-28 verifies the pair rather than skipping the unchanged artifact:
  `release.py verify-versions` must report 0.2.0 for `pyproject.toml`,
  `recipe.yaml` **and** `packages/qgis-sdk-bridge/package.json`, and the bridge
  build, `npm pack --dry-run` and license checks run from the unchanged
  package.

If a bridge change does become necessary in m-1 (a new error code, a contract
version bump forced by a Python wire change), it belongs to this milestone: add
it here, close the task that owns it, and keep the pairing test green. Do not
let an undiscussed bridge delta ride along with the Python delta.

## Version policy

0.2.0 is a SemVer planning target, not a published version. Experimental 0.x
breaking changes require a documented minor release; patches are compatible
fixes. Prereleases may use 0.2.0-alpha.1 or 0.2.0-beta.1. Do not bump manifests
during planning. When the milestone closes, the minor is set **explicitly**
(`release.py plan --bump minor`); feature and fix work inside the milestone only
bumps the patch, so automatic derivation proposes the patch and the milestone
release is a deliberate act. `qgis-sdk` and `qgis-sdk-bridge` are stamped
together at one shared version
([decision-24](../decisions/decision-24%20-%20Release-the-Python-SDK-and-TypeScript-bridge-at-one-shared-version.md));
IPC protocol versions stay independent of it. Stable 1.0.0 requires a later
explicit API-stability decision.
