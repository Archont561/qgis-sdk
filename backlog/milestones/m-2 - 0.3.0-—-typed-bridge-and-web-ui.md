## Description and exit criteria

The milestone where `@archont561/qgis-sdk-bridge` stops being a set of wire
primitives and becomes a runtime: a versioned transport contract over
`QWebChannel`, generated operation-specific clients and validators, thin React
helpers behind a subpath, and per-view authorization that a forged payload
cannot bypass. The Python side grows the matching host half — the allowlisted
router, view/origin/generation binding, subscriptions and resource release.

Exit criteria, both required:

- **`qgis-sdk`** — the host side of the transport is implemented and authorized
  per view; contract fixtures are generated from the Python declarations and
  checked in; layered pytest and BDD fixtures (TASK-7) cover the contract
  without a live browser.
- **`@archont561/qgis-sdk-bridge`** — the generated clients, validators,
  React helpers and authority enforcement are implemented; the root import
  still loads no React, testing helper, `window` or Qt global; the build,
  typecheck, contract suite and coverage gate pass.

## Bridge track

This is the only milestone that changes the bridge's source, and it does so in
four task-sized pieces:

| Task | What lands in `packages/qgis-sdk-bridge` |
| --- | --- |
| [TASK-4](../tasks/task-4%20-%20Add-the-versioned-WebEngine-bridge-contract.md) | The versioned transport contract: allowlisted endpoints, narrow dispatcher, invocation/subscription/stream semantics, borrowed-vs-owned resource release, injected client-local transports |
| [TASK-17](../tasks/task-17%20-%20Generate-checked-in-TypeScript-contracts-clients-and-validators.md) | Generated, checked-in contracts, operation-specific clients and validators — the type-safety guarantee, not a hand-asserted `invoke<T>` |
| [TASK-18](../tasks/task-18%20-%20Add-thin-React-bindings-and-isolated-frontend-test-harnesses.md) | Thin React helpers and isolated frontend harnesses, reachable only through their own subpath |
| [TASK-20](../tasks/task-20%20-%20Enforce-scoped-file-network-and-browser-resource-authority.md) | Client half of scoped file/network/browser-resource authority |

Shape constraints that stay binding: one package with isolated subpath exports
([decision-18](../decisions/decision-18%20-%20Ship-a-framework-neutral-bridge-and-explicit-web-scaffolding-choices.md)),
endpoints declared and allowlisted rather than reflectively invoked
([decision-9](../decisions/decision-9%20-%20Declare-allowlisted-typed-bridge-endpoints-with-runtime-owned-routers.md)),
and the contract version described independently of the package version — a wire
break bumps the contract version, while the package minor advances at this
milestone's close
([decision-25](../decisions/decision-25%20-%20Version-each-package-independently-behind-a-shared-contract-version.md)).

The milestone also has to keep the pair honest: Python and TypeScript validate
the same fixtures (TASK-4 AC #1), so a change to a serialized shape fails on
both sides in the same run instead of drifting until a release gate notices.

Release shape: two tags, two versions — `python-v0.3.0` and `ts-v0.2.0`. Neither
number is derived from the other; both minors are passed explicitly at the
close, and `verify-versions` checks each scope plus the contract version.

## Version policy

0.3.0 is a SemVer planning target, not a published version. Experimental 0.x
breaking changes require a documented minor release; patches are compatible
fixes. Prereleases may use 0.3.0-alpha.1 or 0.3.0-beta.1. Do not bump manifests
during planning. Feature and fix work inside the milestone bumps only the patch;
the minor advances at the milestone close by an explicit `--bump minor`.
`qgis-sdk` and `qgis-sdk-bridge` carry **independent** versions, each derived
from its own commits and stamped by its own release tag ([decision-25](../decisions/decision-25%20-%20Version-each-package-independently-behind-a-shared-contract-version.md));
this milestone releases Python 0.3.0 and the bridge 0.2.0 as two releases with
two explicit minors. A shared plugin-description contract version is what pairs
them. Stable 1.0.0 requires a
later explicit API-stability decision.
